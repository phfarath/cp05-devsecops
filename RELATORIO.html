Objetivo e implementação

O projeto apresenta um site estático servido por um contêiner Nginx. O workflow security.yml executa três jobs independentes a cada push e pull request: Gitleaks, Semgrep e Trivy. As barreiras avaliam segredos no histórico, uso de eval no JavaScript e vulnerabilidades críticas nos componentes da imagem.

O Trivy foi incluído para cobrir o cenário de imagem com CVE crítico, pois o enunciado menciona três jobs, mas nomeia apenas Gitleaks e Semgrep.

Barreira 1: Gitleaks

O Gitleaks procura padrões de segredos no histórico de commits alcançável pela branch analisada. O projeto mantém as regras padrão e acrescenta uma regra para um marcador fictício da CP05, sem acesso a qualquer serviço. O comando usa ocultação de valores nos logs e código de saída 1 quando encontra um segredo. No teste, um arquivo com esse marcador deve reprovar o job. A execução acontece após o push; a proteção de branch com checks obrigatórios é que permite impedir a integração de um pull request reprovado.

Barreira 2: Semgrep

O Semgrep analisa o código JavaScript sem precisar executá-lo. A regra local cp05-no-eval identifica chamadas diretas a eval, que podem executar texto como código. O teste insere uma função que recebe uma entrada e a passa a eval. A opção --error transforma o achado em falha do job. Essa regra cobre o exemplo exigido na atividade, mas não detecta todas as classes de vulnerabilidades de uma aplicação.

Barreira 3: Trivy

O Trivy examina os componentes da imagem construída a partir do Dockerfile e consulta uma base de vulnerabilidades conhecidas. A configuração seleciona severidade CRITICAL e código de saída 1, inclusive para achados sem correção disponível. Assim, um CVE crítico detectado reprova o job. O resultado depende da versão da imagem e da base consultada no momento da análise. Uma falha de construção ou de download não demonstra a detecção de vulnerabilidade.
